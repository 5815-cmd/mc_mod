# 玩家需求汇总（本轮）—— 修仙整合包方向

> 玩家原话整理。**这份是接下来几轮的总蓝图**，逐条跟踪。
> 最终目标：**做成一个修仙整合包**（本 mod 是核心，后期加入精英怪模组等）。

---

## 一、战斗表现

### 1.1 怪物血条

- **所有怪物头顶显示血条**（不是只有名字）
- **强大的 BOSS 要单独一条 BOSS 血条**——像网上那种横贯屏幕上方、
  带名字与阶段刻度的样式
- 血条要能看出**当前/最大**，精英以上建议显示数字

**实现要点**：
- 普通怪：头顶名字下方画一条（用 `RenderNameTagEvent` 或自定义 render layer）
- BOSS：走原版 `ServerBossEvent`（就是末影龙/凋灵那条），
  **按品阶决定颜色**（头目=紫、首领=红）
- **必须客户端渲染**，所以服务端要把血量同步好（原版实体血量本来就同步，够用）

### 1.2 怪物外形多样化

- **多点兽类怪物**（现在只有灵狼、烈焰猿、雷鹰、石傀、虚空蛟算兽）
- **不同品质外观要不一样**——精英和普通不能只差一个名字前缀

**实现要点**：
- 外观差异用**可验证的机制**表达，不是形容词：
  精英加**发光眼睛/粒子**、队长加**体型放大 + 护甲件**、
  头目加**披风/光晕**、首领加**整体放大 + 独特配色**
- 现有 `MobRank` 已有 5 档倍率，把它接到**渲染层**上（scale + 附加部件）
- 新增兽类怪物继续按 `docs/spirit-beast-spec.md` 的"职能分化"原则做

## 二、经济

### 2.1 商店买卖

- 商店**既能买也能卖**
- **挖到的东西、掉落物都能卖**，各自设价格

**实现要点**：
- 现有 `ShopCatalog` 有 `sellPrice` 吗？没有的话加一个**回收价表**
- 价格口径建议：**卖出价 = 买入价的 25%~40%**，防止"买入再卖出"套利
- 覆盖范围：原版矿物/材料 + 本 mod 全部材料（灵叶、灵铁锭、灵晶、空冥精、
  血珞精、灵植花瓣、妖丹…）
- **必须有防套利断言**：任何物品的卖出价都不得高于其买入价

### 2.2 品质系统

- 给物品加**品质**（凡品/良品/上品/极品/仙品之类）
- **"其他的东西增加品质什么的，多一些内容"**——即品质要铺开，不只是丹药

**实现要点**：
- 品质做成**纯数据枚举**（可离线断言）
- 至少覆盖：丹药、法宝、法宝剑、灵植花瓣、妖丹
- 品质影响：丹药效果倍率、法宝属性、卖出价格
- 与既有的**灵根 7 品**、**道宫 6 品**口径保持一致（同一套中文命名体系）

## 三、炼丹雷劫（玩家给了精确数值）

**炼出最好的丹药时，会有一道雷电劈下**：

| 概率 | 结果 |
|---|---|
| **5%** | **失败**（丹药毁掉） |
| **15%** | 一颗变 **5 个** |
| **30%** | 变 **3 个** |
| **50%** | 就给 **1 个** |

**其他品质的丹药**：
- **没有雷劈**
- 但"变五个"的概率是 **20%**

**实现要点**：
- 这套概率必须做成**纯数据表**（`AlchemyTribulation` 之类），离线可断言：
  - 四条概率之和 = 100%
  - 期望产出可计算
- 触发条件：**只有"最好的丹药"**（哪个是最优？按 `AlchemyRecipes` 的品阶 6）
- 表现：真的**劈一道闪电**（`EntityType.LIGHTNING_BOLT` + `setVisualOnly(true)`，
  别用带伤害的），丹药**飞上天**（掉落物上升的动画）再落回
- ⚠️ **别重蹈雷劫必死的覆辙**：这是**炼丹**的雷，**不该伤到玩家**。
  用 `setVisualOnly(true)` 的纯视觉闪电。

## 四、世界生成

### 4.1 全新群系地形

- **全新群系**
- **地面上生成灵植**

**实现要点**：
- 新群系（`data/hongmeng/worldgen/biome/*.json`）+ 对应的地形
- 现有 6 种灵植已有 `biome_modifier`，但只加在**原版群系**上；
  新群系里应该有**更高密度**的灵植
- 建议群系：**灵脉山谷**（灵植密集）/ **荒古战场**（废墟 + 强怪）/
  **云梦泽**（水泽 + 稀有灵植）

### 4.2 建筑要"大气宏伟仙气"

**参考**（玩家要求搜网上建筑）：
- [Minecraft 东亚建筑参考手册](https://kaleidscoper.github.io/2025/10/15/2025-10-15-mc-cn-building/)
- [中式玄幻建筑避坑：飞檐不是房角，斗拱不是越多越好](https://post.smzdm.com/p/a03026w0/)
- [Oriental Fantasy - Mystic Valley Sect（宗派 3D 参考）](https://sketchfab.com/3d-models/oriental-fantasy-mystic-valley-sect-61a8540960584970822aeafaa683717a)
- [MC 建筑指南：大殿建造方案](https://www.snm0516.aisee.tv/video/BV1G6ZjBVEcj/)

**那条"避坑"文章的标题本身就是最重要的设计原则**：
> **飞檐不是房角，斗拱不是越多越好。**

即：**比例与克制**比堆装饰更重要。具体到做法：

| 要点 | 做法 |
|---|---|
| **台基** | 建筑要有**明显的台基**（多层石台），这是中式建筑的骨架 |
| **飞檐** | 屋顶起翘要有**渐变**，不是四角各放一个翘角 |
| **斗拱** | 层数要有节制，密集堆叠反而廉价 |
| **中轴对称** | 主殿居中，配殿对称，**用轴线组织空间** |
| **尺度** | 主殿要**真的高**（≥ 15 格），否则"宏伟"无从谈起 |
| **留白** | 广场、台阶、栏杆——**空的地方也是设计** |

**现有结构的问题**：`xiuxian_yard` 只有 15×9×15，太小了，谈不上宏伟。
需要**新的、更大的**结构（建议 40×30 以上）。

## 六、整合包兼容（重要，影响架构）

玩家明确说：**"我后期会加入那种精英怪模组什么的增加怪物强度增加其他维度什么的
来做成一个修仙整合包"**

**所以必须提前考虑**：

1. **怪物强度不要写死**——现在 `MobScaling` 是按本 mod 的境界缩放，
   要留出**配置文件**让整合包作者调倍率
2. **不要硬编码原版实体 id**——用 **tag**（`#minecraft:undead` 之类）
   或宽松匹配，否则加了精英怪模组会漏掉
3. **维度不要假设只有本 mod 的**——玩家的"其他维度"要能接入
4. **配置项要齐**：`HongmengConfig` 里把各种倍率都暴露出来
5. **别和常见模组冲突**：属性注册用独立命名空间、别覆盖原版行为

## 十、必须守住的既有约束（每条都踩过）

1. **属性上限已解除**，别再引入按名字反射的代码
2. **客户端也要拿到数值**——血条、蓄力条都是客户端画的
3. **怪物伤害软上限 35%** 不能绕过
4. **`RegistryObject.get()` 不能在 mod 构造阶段调用**
5. **`data/**` 的 JSON 写错会让服务器起不来**，改完必须真跑服务端
6. **结构 NBT 的方块名不能带 `[...]`**（要拆成 `Name` + `Properties`），
   否则结构静默不生成
7. **用了 `FlyingMoveControl` 就必须注册 `FLYING_SPEED`**，否则区块里有该实体就崩
8. **新按键必须同时补 `key.hongmeng.*` 与 `key.categories.hongmeng`** 的 lang
9. **离线验证器不能碰注册表**（`Blocks`/`Attributes`/`ItemStack` 静态初始化）
10. **日志检查要 grep 全**——`Couldn't load structure` 这类"不致命但功能失效"的错误
    曾经漏掉过

## 十一、玩家已确认的决定

### 11.1 「最好的丹药」= 最高**品阶**，不是某颗特定的丹

玩家原话：**"丹药是品阶，比如一种丹药有普通和完美这样。"**

即：**丹药按品阶分档**（同一种丹有 普通 / 完美 / 仙品 等不同品阶），
"最好的丹药"指的是**最高品阶那一档**，而不是某颗按名字指定的丹。

现存数据正好对上：修为丹就有 **普通修为丹 / 完美修为丹 / 仙品修为丹** 三档。

实现口径：`AlchemyTribulation.bestTier()` = 全表最高丹方品阶，
当前 = **第 6 阶**，其产物为 **筑基丹** 与 **仙品修为丹**，两条都挨雷。

> 这个口径的好处：以后往表里加更高品阶的丹方，雷劫会**自动跟着上移**，
> 不会出现"加了更强的丹反而没雷劈"的哑火。

### 11.2 建筑按 (c) 走：先程序化铺量，再挑一两座精修

玩家选择 **(c)**。

理由（我给的三个选项）：
- (a) 一两座精雕细琢的主殿 —— 慢但好看
- (b) 多座程序化生成的大体量建筑 —— 快但细节略糙
- **(c) 先 (b) 铺量，之后再挑一两座精修** ← 玩家选这个

执行顺序：先把**体量、台基、中轴对称**做对（这是"宏伟"的骨架），
细节留到精修阶段。骨架对了，糙一点也像样；骨架错了，堆再多装饰也廉价。

### 11.3 领域完善排在最后

玩家原话：**"未完成的做完再做领域。"**

所以顺序是：**先把 P0/P1/P2 清完 → 再做领域**。
